# M4 — Prices & valuation

**Goal:** every market-priced holding values itself each day from public price universes,
without a single request that names an instrument the household holds. Net worth stops being
whatever was last typed in. The app also starts keeping the history that the M5 timeline draws.

Read with: [ADR-0005](../decisions/0005-public-price-feeds.md) (whole universes, manual override),
[ADR-0051](../decisions/0051-record-types-and-common-fields.md) Q6 (`quantity` + `instrument` + manual
`value`), [ADR-0055](../decisions/0055-networth-lenses-and-rounding.md) (lens maths), `docs/UX.md` §2.3
(per-instrument "as of", stale after 36 h), §3.3 (timeline), `docs/api/CONTRACT.md` (`/api/prices/…`).

## What exists after M3

- Priced kinds (`mutualFund`, `stock`, `usStock`, `crypto`, `rsu`) store `quantity` (decimal
  string, 10⁻⁸ units, `src/domain/units.ts`) and `instrument {source: amfi|nse|bse|us|crypto,
  code}`, plus a manual `value`/`asOf` that net worth uses today. `foreignBank` stores
  `balanceMinor` + `currency`. `preciousMetal` stores `weightMg` + `karat`. Tax lots (ADR-0063)
  sum to `quantity`.
- The user types the scheme code or ticker by hand. Nothing checks it.
- `netWorth()` / `allLenses()` take `BalanceItem { value }`, so a valued figure can be swapped in
  before them without changing the lens maths.
- The server has no price code. `GET /api/prices/universe/:kind/:date` is only a line in
  CONTRACT.md.

## Design questions the first issue settles (ADR-0064)

1. **Price representation.** NAVs have 4 decimals, crypto can need 8 or more, and USD prices
   need FX. Recommended: a price is a decimal string per unit in its own currency (the same
   grammar as `quantity`). `units × price × fx` is computed in bigint and rounded half-up to
   paise once, at the end.
2. **Derived, never written back.** A valued figure is computed on read from
   `quantity × price` and is never saved into the record. Saving it daily would make every
   member's device rewrite every holding daily, and whole-record LWW would fight. Recommended:
   yes. The stored `value` stays the manual fallback, used when no price is found.
3. **Sources per universe.** ADR-0005 named Yahoo for Indian equity. NSE/BSE publish a daily
   bhavcopy: one official file per exchange, with no per-symbol calls. Recommended:
   bhavcopy for `nse`/`bse` (ETFs included, which covers gold ETFs); AMFI `NAVAll.txt` for
   `amfi`; a fixed top-N list for `us` and `crypto` that the **server** fetches in bulk (the
   list doesn't depend on any household); Frankfurter for FX. Re-verify every URL in the first
   issue. ADR-0064 amends ADR-0005's table.
4. **Gold & silver.** Per-gram INR rates (24k; other karats prorated) come from the source
   the ADR picks, with a manual-override path. If no reliable whole-file source exists,
   metals stay manual in M4 and the ADR says so.
5. **Universe file format and caching.** One gzipped JSON per `kind` per date:
   `{ kind, date, fetchedAt, source, prices: { code: price } }`. The server keeps the last 400
   days in Postgres. It is public data, so plaintext is fine in its own table, which is never
   joined to households. The client downloads **every** universe each day after unlock (same
   bytes for every household) and keeps them in Dexie. Recommended: the route needs a signed-in
   session (abuse control) but never varies by user.
6. **Ingest schedule.** Production (home server): an in-process scheduler in the Node server,
   one run after the AMFI publish window (~23:00 IST) and one retry in the morning. Staging:
   a Vercel cron hitting a `CRON_SECRET`-guarded route. Recommended: both call one pure
   `ingest(kind, date)` pipeline.
7. **Poisoned or broken feeds.** On ingest, reject a file that parses to < 50% of yesterday's
   instrument count. Flag (don't drop) day-on-day moves over 50%. The previous good file
   keeps serving. The client shows the date it actually has, never a guess.
8. **History for the timeline.** A daily `snapshot` envelope type (new; ADR-0051's list
   gains it): per-lens totals and per-bucket composition, written by the first device to
   open the app that day. Its id is derived from the date under the HDK, so two devices
   converge on one record. Recommended: yes, and the timeline begins at the first snapshot
   (UX §3.3's "starts once you've had two check-ins"). No backfill, which would need
   per-symbol history.

## Scope (one issue each; filed on milestone M4)

1. **ADR-0064 + price maths** (#162, `size:M`, `type:adr`, pure). Settles the questions above.
   `src/domain/prices/`: the price grammar, `valueOf(units, price, fx)` in bigint with
   half-up rounding, and a universe lookup type. Unit tests: NAV × fractional units, tiny
   crypto prices, USD via FX, rounding at the paisa.
2. **AMFI parser** (#163, `size:S`, pure). `NAVAll.txt` → `{code: nav}` by scheme code, with the
   ISIN kept for M6 import matching. Fixture from a real day's file (public data).
3. **NSE/BSE bhavcopy parser** (#164, `size:S`, pure). Equity + ETF close prices by symbol.
4. **US, crypto and FX universes** (#165, `size:M`). Server-side bulk fetch of the fixed top-N
   lists plus Frankfurter. Pure parsers, network at the edge only.
5. **Price store + route** (#166, `size:M`, `area:prices`). Drizzle table + migration, `ingest()`
   with the sanity checks, `GET /api/prices/universe/:kind/:date` (gzip, ETag, immutable for
   past dates), contract tests, CONTRACT.md.
6. **Ingest scheduler** (#167, `size:S`, `area:infra`). In-process schedule for the home server,
   Vercel cron + `CRON_SECRET` for staging, DEPLOYMENT.md steps.
7. **Client price cache** (#168, `size:M`). Dexie table, a daily download of every universe after
   unlock, offline use of the last good set, cleared never (public data).
8. **Valuation on read** (#169, `size:M`). `valuedItems(records, prices)` feeds `netWorth()`.
   Priced kinds, RSU vested units, foreign bank via FX, and metals (if Q4 allows) are
   valued; otherwise the manual value. Home, Accounts and Goals show "as of" per holding, the
   stale tone after 36 h, and "manual value" when no price matched.
9. **Instrument picker** (#170, `size:M`). In Add anything, search the downloaded universe by name
   or code (local, no request) instead of typing a code. It shows today's price and fills the
   value. An unmatched code stays allowed with the manual value.
10. **Daily snapshots** (#171, `size:M`). The `snapshot` type, its date-derived id, a once-a-day
    write, the LWW tie-break, and pure tests. No chart (M5).
11. **M4 acceptance E2E** (#172, `size:S`, `area:security`). Two households with different
    holdings make byte-identical price requests (request log compared). Values match
    fixtures to the paisa. A stale universe shows the warning. The DB scan still finds no
    plaintext.

Order: 1 → 2, 3, 4 (parallel) → 5 → 6, 7 → 8 → 9, 10 → 11.

## Acceptance

- Every priced holding with a matched instrument shows a value computed from that day's
  universe, with its "as of" date. Unmatched ones keep the manual value, labelled as such.
- Net worth per lens matches hand-computed fixtures to the paisa, including FX and
  fractional units.
- No request from the client names an instrument: the price requests of two households with
  different holdings are identical.
- A feed outage leaves the last good prices in use with a visible stale warning. A poisoned
  file (half the instruments missing) is rejected at ingest.
- One snapshot per household per day, whichever devices open the app.

## Out of scope

Charts and the timeline screen (M5), XIRR and returns (M5), accrual calculators for
EPF/PPF/FD and rate tables (M7), per-symbol long-tail fetches (ADR-0005's warned fallback,
M7 if ever), price backfill, statement import (M6), intraday or live prices (never).
