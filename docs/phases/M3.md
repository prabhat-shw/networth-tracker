# M3 — Data model & manual entry

**Goal:** a household can type in everything it owns and owes, jointly or not, and see one
honest net-worth figure per lens (Me · Household · each member). Every value is entered by
hand; M4 adds prices. Every record syncs through the M2 engine as an opaque envelope.

Read with: [ADR-0047](../decisions/0047-record-plaintext-format.md) (plaintext `{type, schemaVersion, data}`),
[ADR-0050](../decisions/0050-sync-wire-up.md) (`useRecords`, `sync.write`),
[ADR-0016](../decisions/0016-features-borrowed-from-other-apps.md) (#25–#27),
`docs/UX.md` §2.1 (ownership lens), §2.3 (sync states), §3.2 (Home), §3.4 (Accounts), §3.5 + §4 (Add anything).

## What exists after M2

- `startHouseholdSync().write(id, type, data, deleted?)` seals and queues one record; `useRecords()`
  returns the live decrypted `PlainRecord[]` (memory only, cleared on lock). LWW is per **whole
  record** (`modifiedAt`, then `modifiedBy`).
- `src/domain/` holds only `money.ts` (paise) and `lww.ts`. No record types, no Zod schemas yet.
- Members come from `GET …/members` as `{ userId, publicKey, joinedAt }`: **no names** (ADR-0031).
- A member without a recovery method can write but nothing pushes (`409`, ADR-0040); the outbox
  gives no signal. M3 must surface this.

## Design questions the first issue settles (ADR-0051)

1. **Granularity of `type`.** (a) ~30 envelope types, one per kind; (b) five types — `member`,
   `asset`, `liability`, `goal`, `transaction` — each a Zod discriminated union on `data.kind`.
   Padding already hides the type from the server, so this is purely a code question.
   Recommended: **(b)**; the 7-bucket picker and the Accounts sections map from `kind`.
2. **Allocations: embedded or separate records?** PLAN.md §1.1 says a separate `allocation`
   record; ARCHITECTURE.md says `allocations[]` on the source record. With whole-record LWW,
   separate records survive two members tagging the same FD at once, but the ≤100% invariant
   can then break after a merge. Recommended: **embedded**, so the invariant is checked per
   write and can never be broken by a merge. The ADR fixes whichever doc loses.
3. **Shares as integers.** `owners[] { memberId, shareBps }` in basis points summing to 10 000,
   not a float `sharePercent`. Same for allocation and nominee percentages. Recommended: yes.
4. **Schema evolution.** Each type has a `schemaVersion` and pure upgrade functions run on read.
   A record with an unknown type, or a newer `schemaVersion` than this build knows, is kept,
   shown as "Needs a newer app version", and never overwritten. Recommended: yes.
5. **Member names.** A `member` record (display name, colour) inside the ciphertext, written by
   each member for themselves. Owners that point at a former member read "Former member".
6. **Market-priced kinds before M4.** Store `quantity` + an instrument key, plus a manual
   `value`/`asOf` fallback that M4's valuation replaces. Recommended: yes, so M4 adds no migration.

## Scope (one issue each; filed on milestone M3)

1. **ADR-0051 + common fields** (#130, `size:M`, `type:adr`, pure). Settles the questions above. Zod
   schemas in `src/domain/records/` for the shared fields: `owners`, `includeInNetWorth`,
   `institution`, `tags`, `notes`, `asOf`, `allocations`, `nominees` (#25's field), plus the
   upgrade/unknown-type rules. Unit tests: shares sum to 10 000, allocations ≤ 100% or ≤ value.
2. **Asset & liability kinds** (#131, `size:M`, pure). Every kind in PLAN.md's taxonomy, with the
   0–3 type-specific fields from UX §4.2. Liabilities: outstanding, EMI, tenure, linked asset.
3. **Typed records layer** (#132, `size:S`). `useAssets()` / `useGoals()` etc. over `useRecords()`:
   parse with Zod, fail soft per record (UX §3.4 error row), and preserve unknown records. Writes
   are validated before `sync.write`. Includes the `member` profile record and a name prompt.
4. **Net-worth engine** (#133, `size:M`, pure, `src/domain/networth.ts`). Per lens: share-weighted
   assets − liabilities, `includeInNetWorth`, unvested RSU and term cover at ₹0, all in paise.
   Unit tests for every lens, joint and solo records, and rounding (bps × paise never floats).
5. **Goals + allocations model** (#134, `size:S`, pure). `goal` schema (PLAN §1.1) and the Unallocated
   remainder per source and per household. The derived metrics (SIP, projections) stay in M5.
6. **Add anything: steps 1–2 + common skeleton** (#135, `size:M`). Sheet (mobile) / dialog (desktop),
   7 buckets, search, the six-field skeleton, the "Owned by" split control with its live remainder chip.
7. **Add anything: per-kind fields + edit** (#136, `size:M`). The type-specific fields, edit and
   delete, "Save & add another", and the optional "Tag to goal" combobox.
8. **Accounts list** (#137, `size:M`). UX §3.4: grouped mobile list with ownership badges, dense
   desktop table, search, empty and error rows.
9. **Home with real net worth + sync status** (#138, `size:M`). UX §3.2 hero with the lens toggle and
   the first-run CTA; settles #34's "Home fits one screen". UX §2.3 sync indicator, including a
   "Changes are waiting: add a recovery method" state for the ADR-0040 `409`.
10. **Goals screen (basic)** (#139, `size:S`). Create, edit and delete a goal; list with current earmarked
    total and Unallocated. The allocation editor and auto-tag rules are M5.
11. **#25 nominees** (`size:S`): the form field on top of item 1's schema.
12. **#26 tax lots** (`size:M`): lots on holdings, FIFO consumption, manual lot entry.
13. **#27 linked transfers** (`size:S`): the `transaction` type with `transferId`, plus an ADR.
14. **M3 acceptance E2E** (#140, `size:S`, `area:security`). Two members add a joint FD (50/50) and a solo
    PPF; each sees the right Me/Household figures on both devices. DB plaintext scan finds no
    names, amounts or kinds; cross-household isolation still holds.

Order: 1 → 2, 3, 5 (parallel) → 4 → 6 → 7 → 8, 9, 10 → 11–13 → 14.

## Acceptance

- Every PLAN.md taxonomy kind can be added, edited and deleted by hand, with ownership shares.
- Net worth for Me, Household and each member matches hand-computed fixtures to the paisa.
- A joint record shows its ownership badge everywhere it appears; shares and allocations
  can't be saved invalid.
- A record from a newer schema or unknown type survives a round trip untouched.
- Edits stuck behind `409 recovery-required` are visible to the member who made them.
- The E2E DB scan and the IndexedDB leak scan find no plaintext; the payload is padded as in M2.

## Out of scope

Prices and automatic valuation (M4), charts and the timeline (M5), allocation editor, auto-tag
rules and goal maths (M5), statement import (M6), accrual calculators and RSU vesting maths (M7),
attachments (M6), change history beyond LWW, field-level merge.
