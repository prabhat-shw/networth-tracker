# M2 — Encrypted sync engine

**Goal:** records written on one device appear, decrypted, on every other member's device,
including after time offline. The server stores and relays opaque envelopes and never merges.
No financial record types yet: M2 syncs a generic record whose type lives inside the
ciphertext. M3 adds the real types on top.

Read with: [ADR-0003](../decisions/0003-sync-protocol.md) (sync protocol),
[ADR-0013](../decisions/0013-crypto-primitives-and-envelope.md) (envelope, `recordAad`),
[ADR-0021](../decisions/0021-household-authorisation.md) (guard), [ADR-0040](../decisions/0040-recovery-method-before-first-data.md)
(push needs a recovery method), `docs/api/CONTRACT.md` (records section).

## What exists after M1

- `records` table: `id, household_id, version, updated_at, ciphertext, deleted`, indexed on
  `(household_id, version)`. Read path `GET /api/households/:id/records?since=N`
  (`src/server/records.ts`): guarded, 500 per page, ascending `version`.
- `seal`/`open` with AAD `recordAad(id, version)` and the HDK's kid (`src/crypto/aead.ts`).
- `requireRecoveryMethod(db, userId)` (`src/server/vault.ts`) answers `409 recovery-required`.
- E2E record probe (ADR-0036): seals in the browser, while the spec inserts with SQL in place of
  push. **M2 replaces the SQL insert with the real push.**

## Design questions the first issue settles (ADR-0045)

1. **Version vs cursor.** AAD binds `version`, so the client must know it before sealing, but
   `pull(since)` needs a household-wide monotonic cursor. Options:
   - (a) The per-record `version` is set by the client to `base + 1`. The server accepts it
     only if the stored version is `base`, and a separate server `seq` (bigint, household-wide)
     is the pull cursor. This adds one opaque column, so the CLAUDE.md invariant needs amending.
   - (b) `version` is itself the household-wide sequence. The client reserves a number
     first, which costs an extra round trip and leaves gaps on failure.
   - (c) Drop `version` from the AAD and bind the record id only. This loses rollback
     protection.

   Recommended: **(a)**.
2. **LWW clock.** The server-stamped `updated_at` drives the cursor only. The merge uses
   `modifiedAt` + `modifiedBy` *inside* the plaintext (the client clock), so the server learns
   nothing more.
3. **Routes.** Household-scoped (`…/households/:id/records` GET + POST) to match the guard,
   rather than the placeholder `/api/sync/pull|push` in CONTRACT.md.
4. **Limits.** Max records per push, max ciphertext bytes per record, and padding of
   ciphertext lengths so sizes don't hint at record types. Recommended: pad to 256-byte buckets.

## Scope (one issue each; filed on milestone M2)

1. **ADR-0045 + contract** (#113, `size:S`, `type:adr`). Settles the questions above and writes
   the records section of `docs/api/CONTRACT.md` as the spec (push request/response, 409
   body, limits, errors), amending the CLAUDE.md invariant if (a) is chosen.
2. **Server push** (#114, `size:M`, `area:sync`, `area:security`). `POST …/records`: guard first,
   `requireRecoveryMethod`, then validate the shape and limits, and apply atomically in one
   transaction with per-record optimistic concurrency. Each record is either applied, with
   its new cursor, or comes back as a conflict carrying the server's current envelope.
   Migration for the cursor column if needed. PGlite tests: stale base → conflict, cross-household 404,
   no recovery slot → 409, an oversized record → 400, and concurrent pushes never share a cursor.
3. **Record codec + merge** (#115, `size:M`, `area:crypto`, `area:sync`, pure). Plaintext
   `{ type, schemaVersion, data, modifiedAt, modifiedBy }` → padded → sealed under the HDK
   with `recordAad(id, version)`. `decodeRecord` fails closed (`DecryptError`). Pure
   `mergeLww(local, remote)` and tombstone handling. Unit tests: round trip, a wrong
   household key, version swap and replay are all rejected, LWW ties are broken by `modifiedBy`.
4. **Local store (Dexie)** (#116, `size:M`, `area:sync`). Add `dexie` (Apache-2.0: AGPL-compatible).
   It holds per-household envelopes (ciphertext only), the outbox and the pull cursor. Plaintext
   lives in memory only and is dropped on lock. Browser tests: no plaintext in IndexedDB, and lock
   clears the memory cache. Updates the E2E leak scan's IndexedDB allow-list.
5. **Sync engine** (#117, `size:M`, `area:sync`). Pure engine over injected transport and store:
   pull to the cursor, push the outbox, then on conflict re-pull → merge → retry (bounded).
   Runs after unlock, on `online`, and on an interval while visible. Tombstone GC after N days
   once every device has pulled past them. Unit tests with a fake server: two devices with
   offline edits converge, and a delete propagates.
6. **Wire-up + acceptance** (#118, `size:M`, `area:security`). The key session starts sync, and the
   probe seals through the engine, so the spec's SQL insert is gone. E2E: A writes offline,
   comes online, and B sees it. A conflicting edit resolves LWW on both. The DB plaintext scan
   and cross-household isolation still pass. ADR-0036 is amended to say the probe now uses push.

Order: 1 → 2 and 3 (independent) → 4 → 5 → 6.

## Acceptance

- Two members on two devices each converge to the same decrypted record set after offline
  edits on both; deletes propagate.
- The server stores only `id, household, version, cursor, updatedAt, ciphertext, deleted`,
  and the E2E DB scan finds no plaintext. Ciphertext lengths are padded.
- A push from a vault without a recovery method gets `409 recovery-required`, and nothing is written.
- A push or pull for another household is a `404` (ADR-0021).
- Tampered, replayed or version-swapped envelopes fail closed on the client.
- `docs/api/CONTRACT.md` records section is the spec, covered by PGlite contract tests.

## Out of scope

Financial record types and their UI (M3), on-device change history beyond LWW (M3, with the
record screens), attachments/blobs (M6), HDK rotation, social recovery (#112), real-time push
(websockets/SSE).
