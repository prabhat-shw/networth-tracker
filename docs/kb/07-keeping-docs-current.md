# 7. Keeping the documentation current

Documentation rots when nothing breaks as it goes stale. This project makes staleness a
**build failure** wherever that is possible, and a habit everywhere else.

## Layer 1 — automated checks (CI fails)

`pnpm check:docs` and `pnpm docs:check` run on every pull request.

| Check | What it catches |
| --- | --- |
| **Size caps** | `CLAUDE.md` > 120 lines, `docs/STATE.md` > 80, a phase brief > 150, an ADR > 60. Caps keep the per-session reading budget real (see [`docs/CONTEXT.md`](../CONTEXT.md)) |
| **Link integrity** | Every relative Markdown link in the repo resolves to a real file. Renaming or deleting a doc without fixing its referrers fails the build |
| **ADR hygiene** | Filenames are `NNNN-kebab-slug.md`, numbers are unique, each ADR has a `**Status:**` line |
| **Generated README block** | The status table in `README.md` is generated from `package.json` and `docs/STATE.md`. If it drifts, CI fails and `pnpm docs:sync` fixes it |
| **State freshness** | A PR that changes `src/**` must also change `docs/STATE.md`. Code moved; the handoff note has to move with it |

## Layer 2 — process (the checklist)

The [pull request template](../../.github/pull_request_template.md) and the definition of
done in [`CLAUDE.md`](../../CLAUDE.md) both require, for every issue:

- an **ADR** when a decision was made — in the same PR as the change it explains
- **`docs/STATE.md`** rewritten for the next session
- one line appended to **`docs/SESSION_LOG.md`**
- **`docs/PLAN.md`** updated when scope changes

The `/handoff` command walks through this so it does not depend on memory.

## Layer 3 — ownership (which doc answers which question)

Each document has one job. When something changes, this table says what to update:

| Document | Its one job | Update it when |
| --- | --- | --- |
| `README.md` | First impression, quick start | Setup steps, commands or the pitch change |
| `docs/STATE.md` | Where the build is *right now* | Every session, without exception |
| `docs/PLAN.md` | The full plan and roadmap | Scope, milestones or strategy change |
| `docs/ARCHITECTURE.md` | How the pieces fit | A layer, boundary or data-model change |
| `docs/SECURITY.md` | Threat model and controls | Anything touching keys, storage or network |
| `docs/UX.md` | The design being implemented | A screen or interaction is designed or revised |
| `docs/api/CONTRACT.md` | The server contract | An endpoint or payload changes |
| `docs/DEPLOYMENT.md` | How to deploy, exactly | Deploy steps or environment change |
| `docs/decisions/` | Why, permanently | A decision is made, or reversed |
| `docs/kb/` | Explaining the app to newcomers | A concept becomes wrong or a new one appears |
| `CHANGELOG.md` | What shipped | Every user-visible change |

**ADRs are never edited to hide history.** A reversed decision gets a new ADR that supersedes
the old one, and the old one is marked Superseded. The record of what we believed and when is
worth more than a tidy directory.

## Layer 4 — periodic review

At the end of each milestone, `/handoff` includes a documentation pass:

1. Does `README.md` still describe what the app actually does?
2. Does the knowledge base explain anything that has since changed?
3. Are there ADRs describing an approach we quietly abandoned?
4. Does `docs/PLAN.md` still match the roadmap we are following?

Ten minutes per milestone, versus a rewrite when the docs are a year adrift.

## What is deliberately not automated

- **Prose quality.** A link checker cannot tell whether an explanation is any good. That is
  what the milestone review is for.
- **Screenshots.** None are committed yet; when they arrive they will be generated by
  Playwright rather than pasted by hand, so they cannot silently go stale.
- **External links.** Not checked in CI — the network is flaky and a red build caused by
  someone else's outage teaches the wrong lesson.
